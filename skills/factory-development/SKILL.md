# Factory development and self-improvement

Use this Skill when developmental pressure should become a bounded Factory Run, including proposals to improve a native product or its authoritative Skill source.

## Contract metadata

- Semantic ref: `factory:developer`
- Native owner: Software Factory
- Native read/action surface: `factory/` public Run/Build contracts
- Project-development relation: `factory.project-development/v1`
- Structural-ground relation: `factory.structural-ground/v1`
- Fixtures: `skills/fixtures/product-improvement.json`, `skills/fixtures/skill-revision.json`
- Verification: `python3 scripts/validate_factory_skills.py` plus Factory Rust baseline
- Risk class: repository/development proposal; no automatic promotion

## Development law

Factory coordinates development; it does not acquire arbitrary authority over the Project or product it is changing. Recover what the Project is before locally convenient feature decomposition becomes architectural authority. Locate native owners and consume their authoritative public contracts. Generated/projected artifacts and installed runtime state are not the normal authoring source.

For product-meaning work, orient through the smallest sufficient chain actually present:

```text
human-authored Ground / intended experience
  -> SemanticWiki / Project vocabulary
  -> StructuralGround where applicable
  -> semantic <-> local-description <-> exact-code anchors
  -> Project praxis / capability condition
  -> current frontier
```

ProjectCentral, SemanticWiki, ProjectMap, CodeIndex, Skill/Method resolution and Actuation Agency remain owned by their native systems. Factory retains attributable refs and evidence; it does not recreate their stores or resolvers.

## Procedure

1. **Receive pressure as evidence, not command truth.** Record the observation/request and its provenance. A relation-field observation, benchmark result or repeated use may open investigation; none automatically creates a backlog item or mutation.
2. **Recover Project meaning and ownership.** Confirm Project / Focus. Where product meaning matters, read human-authored Ground before deep architecture work. Traverse maintained semantic knowledge and applicable local structural source before treating code-local decomposition as design authority. Identify the repository/product that owns the concept, Action or Skill source.
3. **Retain exact reflection anchors.** Where AIKit/ProjectMap reflection is available, retain only the semantic ref, attributable local source ref, exact CodeReference(s), verification refs and provider revision materially used. A local description is source/contract material, not implementation truth; derived code topology is implementation intelligence, not authored meaning.
4. **Resolve praxis through its owner.** Use AIKit-owned Method/Skill/SkillSet/Profile/UsageOverlay/Context resolution where present. Record the smallest sufficient resolved condition for a consequential Run; do not parse generated harness state into a Factory-local Method or Skill store.
5. **Form the developmental Claim.** State what appears deficient, desired or uncertain, what evidence supports it, and what would falsify or satisfy the Claim.
6. **Open a bounded Run.** Give it a destination, RunMap frontier, expected owner seam and evidence/Recognition criteria. A Run may request Execution from AIKit/Workcell, but the Run itself is not host/repository authority or generic Actuation Agency.
7. **Develop a Candidate through the owner's public seam.** Use owner SDK/domain/application contracts. Do not teach direct mutation of generated projections, installed caches or private foreign state as the default path.
8. **Gather representative evidence.** Run owner-native validation/conformance plus the scenario that motivated the change. Preserve source revision, semantic/code anchors, Execution/material refs and negative/adversarial evidence where authority, structural fidelity or safety matters.
9. **Check returned intelligibility.** After meaningful structural change, ask whether an applicable local description, governance source, ProjectMap relation, Wiki account or verification account became stale. Do not force every edit to rewrite documentation; do not leave an existing durable articulation silently less intelligible.
10. **Return the attributable difference.** Present Candidate, Claims, Evidence, trade-offs, reflection/praxis discrepancy and owner-source diff/revision. Project-reflection discrepancy and praxis fitness are returned evidence, not automatic source mutation.
11. **Promote explicitly or return.** Wiki/source/Ground/Skill/Method pressure returns as a proposal to the native owner and, where required, human Recognition. Successful execution, model scoring, repeated use and benchmark wins are fitness evidence only.

## Native Skill revision procedure

For Skill development, preserve the full chain:

```text
native Skill source + exact revision
  -> observed deficiency / request
  -> Factory Claim + bounded Run
  -> proposed owner-source Skill revision
  -> Skill validation + representative use/evidence
  -> native-owner review / Recognition
  -> explicit promotion, rollback point retained
```

Praxis configuration is an input condition. Praxis fitness is returned evidence. Never treat an edited harness projection as canonical source. Never let `SkillSet` selection imply Root position or metagency. Never convert successful use into automatic trust.

## Structural fidelity

If the target has constitutive structural source, compose with `StructuralGround` rather than assuming name-level parity. Distinguish source, identity/coordinate, relation, operational and experiential fidelity. If a declared source/code relation is stale, record the discrepancy and route a proposal to the source owner; do not silently rewrite the source or flatten a target-owned coordinate into generic Factory ontology.

## Relational field seam

A composed product-relation observation may be consumed as a source of developmental pressure:

```text
relation observation -> possible Claim / investigation / no-change
```

Do not make 144 cells an automatic backlog, an authority engine, or a replacement for QL-MEF formal ownership. QL affinity can inform a capability/praxis relation; it is never activation authority.
