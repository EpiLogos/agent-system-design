# Factory development and self-improvement

Use this Skill when developmental pressure should become a bounded Factory Run, including proposals to improve a native product or its authoritative Skill source.

## Contract metadata

- Semantic ref: `factory:developer`
- Native owner: Software Factory
- Native read/action surface: `factory/` public Run/Build contracts
- Fixtures: `skills/fixtures/product-improvement.json`, `skills/fixtures/skill-revision.json`
- Verification: `python3 scripts/validate_factory_skills.py` plus Factory Rust baseline
- Risk class: repository/development proposal; no automatic promotion

## Development law

Factory coordinates development; it does not acquire arbitrary authority over the product it is changing. Locate the native owner first and consume its authoritative Skill/public contract. Generated/projected artifacts and installed runtime state are not the normal authoring source.

## Procedure

1. **Receive pressure as evidence, not command truth.** Record the observation/request and its provenance. A relation-field observation, benchmark result or repeated use may open investigation; none automatically creates a backlog item or mutation.
2. **Locate the native owner.** Identify the repository/product that owns the concept, Action or Skill source. Resolve the owner Skill and exact source revision. If ownership is ambiguous, create a bounded investigation rather than editing several products opportunistically.
3. **Form the developmental Claim.** State what appears deficient, desired or uncertain, what evidence supports it, and what would falsify or satisfy the Claim.
4. **Open a bounded Run.** Give it a destination, RunMap frontier, expected owner seam and evidence/Recognition criteria. A Run may request Execution from AIKit/Workcell, but the Run itself is not host/repository authority.
5. **Develop a Candidate through the owner's public seam.** Use owner SDK/domain/application contracts. Do not teach direct mutation of generated projection, installed caches or private foreign state as the default path.
6. **Gather representative evidence.** Run owner-native validation/conformance plus the scenario that motivated the change. Preserve source revision, Execution/material refs and negative/adversarial evidence where authority or safety matters.
7. **Return the attributable difference.** Present Candidate, Claims, Evidence, trade-offs and owner-source diff/revision to the owner/human Recognition boundary.
8. **Promote explicitly or return.** Owner review/Recognition may accept, reject or request revision. Successful execution, model scoring, repeated use and benchmark wins are fitness evidence only.

## Native Skill revision procedure

For Skill development, preserve the full chain:

```text
native Skill source + exact revision
  -> observed deficiency / request
  -> Factory Claim + bounded Run
  -> proposed owner-source Skill revision
  -> Skill validation + representative use/evidence
  -> native-owner review / Recognition
  -> explicit promotion, rollback point retained
```

Never treat an edited harness projection as canonical source. Never let `SkillSet` selection imply Root position or metagency. Never convert successful use into automatic trust.

## Product-improvement fixture

`skills/fixtures/product-improvement.json` fixes the owner-routing invariant: an example Workcell improvement begins from a Workcell-owned Skill/public seam, moves through Factory Claim/Run/Candidate/Evidence, and returns to Workcell owner Recognition without direct foreign private mutation.

## Skill-revision fixture

`skills/fixtures/skill-revision.json` fixes source/projection/promotion separation. The authoritative source revision remains named throughout the Run; validation and representative use are evidence; only explicit native-owner promotion changes the canonical revision.

## Relational field seam

A composed product-relation observation may be consumed as a source of developmental pressure:

```text
relation observation -> possible Claim / investigation / no-change
```

Do not make 144 cells an automatic backlog, an authority engine, or a replacement for QL-MEF formal ownership.
